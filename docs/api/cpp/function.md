# Function

`pjrt::Function` is one compiled JAX function together with the storage its
inputs and outputs live in. Loading does all the checking: the sidecar is read
and cross-checked against the executable, every input and output gets its own
64-byte-aligned arena, each input arena is wrapped once in a zero-copy
`PJRT_Buffer`, and the warm-up calls fault in the pages and warm the runtime's
lazy state. A call is then execute, one await, and one `memcpy` per output read
straight out of device memory. Nothing on that path allocates, locks, logs or
flushes.

Both halves of the storage belong to the object. The input arenas live as long
as the `Function` and are the memory XLA actually reads — a call transfers
nothing. The output arenas are overwritten by the next call, so a pointer from
{cpp:func}`~pjrt::Function::output` is valid until then and no longer. Indices
are the sidecar's, which are JAX's argument and result order; resolve names to
indices once at startup with {cpp:func}`~pjrt::Function::find_input`, which is
a linear scan over strings and has no business in a loop.

Two rules the type cannot enforce for you. **Write the inputs between calls,
never during one:** the PJRT buffers alias the arenas for the life of the
`Function`, and XLA is reading them while `call()` runs, so writing from
another thread or a signal handler mid-call is a data race on the
computation's own operands. Between calls it is safe — nothing is in flight —
and that is a deliberate, verified bend of the PJRT host-buffer contract, which
speaks only about mutation while a transfer is outstanding. **One `Function`
per thread:** it owns fixed storage and the executable's per-call state, so
share the {doc}`Runtime <runtime>` instead and give each thread its own
`Function` loaded from the same artifact.

## Options

```{doxygenstruct} pjrt::FunctionOptions
:members: warmup_calls, check_metadata, debug, check_values, load_policy, isa_guard, compile_options
```

`check_metadata` is on by default because a sidecar that has gone stale
relative to its executable is otherwise a buffer-overrun class of bug,
discovered later as corrupted output. Never answer a load failure by turning it
off; answer it with the `.mlirbc` fallback or a re-export.

The warm-up runs with `check_values` off whatever the option says, and
checking starts with the first call after it. An all-zero input can
legitimately produce a non-finite result — a solve against a zero matrix, a
division by a zero parameter — and the warm-up's job is to fault in pages and
lazy state, not to judge values.

## Where the executable came from

```{doxygenenum} pjrt::LoadPolicy
```

```{doxygenenum} pjrt::LoadKind
```

A `.binpb` embeds machine code generated by the exporting machine.
`PJRT_Executable_DeserializeAndLoad` relinks it and never recompiles, which is
why a `.binpb` is locked to that machine's architecture and instruction set,
and why the `.mlirbc` exists. Under `LoadPolicy::Auto` the ISA guard compares
the sidecar's recorded `isa_level` against this host and passes over a `.binpb`
built for a wider instruction set; without the guard the failure is an illegal
instruction somewhere inside the executable, with no hint that the artifact came
from a newer machine. A deployment usually wants `LoadPolicy::BinaryOnly`,
because a fallback that quietly compiles for seconds is not a fallback in a
control loop. {cpp:func}`~pjrt::Function::load_detail` says which file was
loaded and why, including the reason a `.binpb` was passed over.

## One input or output

```{doxygenstruct} pjrt::ArraySpec
:members: name, dtype, shape, numel, nbytes, donated
```

`nbytes` is the size of the arena and the length of the per-call `memcpy`;
`numel` is 1 for a scalar, whose `shape` is empty. A v1 sidecar carried no
names, so those specs come back as `arg<i>` and `out<i>`.

## The function

```{doxygenclass} pjrt::Function
:members: Function, name, num_inputs, num_outputs, input_spec, output_spec, find_input, find_output, input_dtype, output_dtype, input_shape, output_shape, input_rank, output_rank, input_numel, output_numel, input_nbytes, output_nbytes, load_kind, load_detail, fingerprint, options, input_raw, output_raw, input, output, call
```

The destructor destroys the executable and the input buffers and frees the
arenas, so every pointer handed out by `input`, `output`, `input_raw` and
`output_raw` dangles from that moment.

`fingerprint()` is `PJRT_Executable_Fingerprint`, empty when the plugin does
not implement it. Two processes reporting the same fingerprint are running the
same compiled program, which is the cheap way to confirm that a benchmark and a
deployment agree about what they are timing.

## Debug mode

With `FunctionOptions::debug` off, `input<T>(i)` is one indexed load and a
cast, and the branch that would have checked it is on a member that is always
in cache and always predicted. With it on, four classes of mistake become
exceptions instead:

| Check | Raised as | Catches |
|---|---|---|
| index against `num_inputs()` / `num_outputs()` | `std::out_of_range` | an index past the end of the arena table |
| `T` against the declared dtype | `std::invalid_argument` | an artifact re-exported as float32 under calling code that still says `double` |
| re-entrant `call()` | `std::logic_error` | calling from inside a callback the computation itself invoked |
| non-finite float, non-0/1 bool (`check_values`) | `std::domain_error` | a nan arriving from the caller, or leaving the computation |

State the trade plainly: with debug off, the same mistakes are silent memory
corruption. Run with `debug` on in development and in acceptance tests, and
turn it off for the timed loop. `check_values` walks every element of every
arena on every call, so it belongs in a test and never in a control loop; it
runs before and after each call precisely so a bad value can be attributed to
the caller or to the computation.

`input_spec` and `output_spec` are the exception to all of this: their index is
checked in every build, debug or not, because they are startup code and a wrong
index there is worth catching even in a release binary.
